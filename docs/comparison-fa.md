# مقایسه و مسیر ادامهٔ WoHinDamit

تاریخ بررسی: ۱۵ اکتبر ۲۰۲۶. مبنا: فرانت Mani در کامیت 6d4f19f و بکاپ محلی نوشین در کامیت 727dd37. این بررسی ادعای به‌روز بودن مخزن آنلاین نوشین را ندارد.

## نتیجه

فرانت شما HTML/CSS/JavaScript است. بک‌اند نوشین Java 17، Spring Boot، Maven و PostgreSQL است. منظور از اتصال، استفاده از API همین بک‌اند است؛ پروژهٔ Node.js در این بکاپ وجود ندارد.

| بخش | فرانت قبلی شما | بک‌اند محلی | تصمیم نسخهٔ مشترک |
|---|---|---|---|
| شناسایی وسیله | چهار نام ثابت در `geraete` | مدل Item و سرویس موجود؛ کنترلر جست‌وجو وجود ندارد | فعلاً انتخاب دسته از API؛ جست‌وجوی واقعی مرحلهٔ بعد |
| سؤال‌ها | دو select ثابت با مقدار ja/nein | سؤال‌های دسته و انواع جواب از API | ساخت فرم از سؤال‌های سرور و ارسال boolean واقعی |
| توصیه | شرط‌های if/else در مرورگر | DecisionService و قواعد دیتابیس | فقط سرور تصمیم می‌گیرد |
| مراکز | سه مرکز ساختگی؛ همیشه فیلتر الکترونیک | API مراکز و مراکز مرتبط با itemId وجود دارد | تا شناسایی item و ارتباط با action کامل نشده، مرکز مناسب نمایش نمی‌دهیم |
| ظاهر | زمینهٔ سبز و عنوان فعلی | پیش‌نمایش API در پوشهٔ preview | CSS شما پایهٔ صفحهٔ مشترک؛ فرم واکنش‌گرا و وضعیت خطا اضافه شده |

## تغییرهایی که برای ادامهٔ فرانت لازم است

1. `geraete` و منطق توصیهٔ `searchItem` را در نسخهٔ مشترک دوباره پیاده نکنید. اکنون `/api/categories`، سؤال‌ها و `/api/decisions` جایگزین آن‌ها هستند.
2. پاسخ‌ها را با `question.code` بفرستید؛ مقدار فارسی/آلمانی نمایشی را به جای true/false ارسال نکنید. `categoryId` باید از سرور بیاید و ثابت نباشد.
3. فعلاً هر دو سؤال اجباری نمایش داده می‌شوند. در دادهٔ نمونه repairable حتی برای وسیلهٔ سالم اجباری است؛ برای پنهان کردن آن ابتدا مدل سؤال/اعتبارسنجی بک‌اند باید با نوشین هماهنگ شود.
4. جست‌وجوی نام وسیله نیاز به `GET /api/items/search?q=...` و DTO شامل id/name/categoryId دارد. این قرارداد پیشنهادی است و هنوز پیاده نشده؛ تا آن زمان نگاشت حدسی Handy به ID دیتابیس انجام نشود.
5. پس از جست‌وجوی واقعی، itemId را در تصمیم ارسال کنید. مرکز مناسب باید هم با وسیله و هم نوع توصیه سازگار باشد؛ `/api/items/{itemId}/locations` فعلاً فقط ارتباط وسیله/مرکز را نشان می‌دهد و نباید برای هر توصیه بدون بررسی استفاده شود.
6. نقشه، فیلتر منطقه، داده‌های واقعی وین و زمان به‌روزرسانی داده‌ها هنوز لازم‌اند. مراکز نمونهٔ فرانت قبلی دادهٔ واقعی نیستند.
7. وضعیت بارگذاری، فهرست خالی، 400، 404 بدون قاعده و قطع ارتباط باید در فرانت مدیریت شوند؛ جریان منتقل‌شده از پیش‌نمایش این وضعیت‌ها را پوشش می‌دهد.

## تقسیم کار پیشنهادی

- Mani: ظاهر، دسترس‌پذیری، نمایش سؤال‌ها و نتایج، و پس از آماده شدن قرارداد، جست‌وجو و نقشه.
- Noushin: قواعد تصمیم، اعتبارسنجی، جست‌وجوی Item، ارتباط action با مراکز و داده‌های معتبر.
- مشترک: نام APIها، required بودن سؤال‌ها و شکل خطاها را قبل از توسعهٔ بعدی تثبیت کنید.

## نکتهٔ مستندات

`backend/docs/api.md` برخی APIهای مراکز را هنوز «برنامه‌ریزی‌شده» می‌نامد، اما کنترلرهای LocationController، LocationTypeController و ItemLocationController در کد موجودند. برای وضعیت پیاده‌سازی، کد مبناست؛ مستندات باید هماهنگ شود. بکاپ شامل پیش‌نمایش و دادهٔ نمونه‌ای است که در جلسهٔ ۱۲ اکتبر اضافه شده؛ تمام فایل‌ها صرفاً نوشتهٔ اولیهٔ نوشین نیستند.
